# 阶段二：数据诊断与归因判定 (Data Diagnosis)

本文件是 RDHS 体系的**诊断归因引擎**，解决“拿到数据后如何定位病根、如何判断节拍失调”的核心逻辑。

---

## 一、 四级治理分档定义

$$RDHS(100') = 链路闭环(25') + 交付闭环(15') + 时效节奏(20') + 颗粒度对齐(20') + 质量敏锐度(20')$$

| RDHS 分值 | 治理分档 | 治理优先级 | 业务导向 |
|---|---|:--:|---|
| **< 45 分** | **重点治理** | P0 | 存在严重过程脱节、数据断层或重度积压，接口人必须介入整改 |
| **45 ~ 59.9 分** | **风险改进** | P1 | 核心流程通畅但存在单项突出短板（如积压率高、严重缺陷超标） |
| **60 ~ 69.9 分** | **持续优化** | P2 | 准达标产品，各项基本功规范，聚焦时效节奏微调以冲刺达标 |
| **≥ 70 分** | **常规跟踪** | 达标 | 达到健康基准线，常规监控指标稳定性 |

---

## 二、 7 阶归因决策树（按优先级自上而下匹配，首个命中生效）

```text
[有效参与人数 == 0] ───────────────────────> 【过程数据缺失】 ──> 核实阶段、参与和角色，不直接判角色缺失
   └─ 否
       ├─ [人均吞吐 == 0 或 链路得分 < 15] ──> 【价值链路不完整】 ──> 分别描述零吞吐或低链路分
       │       ├─ [人均缺陷关闭量 > 0] ──> 有缺陷关闭无需求完成记录，核实验收及关联
       │       └─ [人均缺陷关闭量 == 0] ──> 吞吐与缺陷均为 0，核实阶段与登记
       ├─ [积压需求占比 > 30%] ─────────────> 【需求积压】 ───────> 节拍失调: ② 在途失控（僵尸需求超期滞留）
       ├─ [严重缺陷占比 > 15%] ─────────────> 【质量管理风险】 ───> 节拍失调: ③ 质量失守（严重致命缺陷超标）
       ├─ [交付闭环得分 < 8] ───────────────> 【发布闭环不足】 ───> 节拍失调: ④ 发版脱节（发版未挂发布计划）
       ├─ [时效节奏合理性 < 10] ────────────> 【研发节奏偏慢】 ───> 拆查周期比值和积压，不直接认定绝对周期长
       └─ 其他 ─────────────────────────────> 【过程能力优化】 ───> 节拍失调: ① 拆解粗糙（单需求包袱过大）
```

### 积压叠加判定规则
若主问题标签不是【需求积压】，但 `积压需求占比 > 30%`，必须在主问题后显式追加：
`叠加积压风险（需求总量 X 个，积压占比 Y%）`。

---

归因标签不是P0/P1分档：治理分档只按有效RDHS判断。正吞吐但链路得分低不能写成吞吐0；缺行和占位不等于真实0分，遵循 SKILL.md。比例及周期变化需核实两侧各自样本，不能直接归因治理效果。

## 三、 五维组件状态诊断标尺

根据各维度得分率（实际得分 ÷ 满分）判断组件健康状态：
- 得分率 $\ge 80\%$：**正常 / 优秀**（绿标）
- $50\% \le$ 得分率 $< 80\%$：**中游 / 偏低**（黄标）
- 得分率 $< 50\%$：**严重偏低 / 缺失**（红标）
